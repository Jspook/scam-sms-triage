# scam-sms-triage

A small data pipeline plus a baseline model that triages scam-SMS reports, so the reports most likely to be real scams get reviewed first.

> **Status:** Phase 0 (skeleton). See [docs/ROADMAP.md](docs/ROADMAP.md).

## Problem

Mobile operators receive a steady stream of reports about suspicious SMS (for example, a hotline where customers report scam numbers and messages). Every report needs checking, and the volume is high. A phishing SMS that imitates the operator's brand (a lookalike domain such as `ais-points-xxx.com`) is usually a higher-priority case than an ordinary spam message.

This project asks one narrow question: **given a stream of SMS reports, which should be reviewed first?**

## Scope

| In scope | Out of scope |
|---|---|
| Batch pipeline: raw report files → DuckDB → clean → mart | Streaming (Kafka), orchestration (Airflow) |
| Data quality checks (nulls, duplicates, out-of-range values) | Real-time blocking, anything touching a live network |
| URL features + text features → baseline classifier | Deep learning, LLMs |
| Priority score → ranked triage table | Production deployment |

## Data: what is real and what is synthetic

| Component | Source | Why |
|---|---|---|
| Report stream (`data/raw/reports_*.csv`) | **Synthetic**, generated by `src/generate_reports.py` | No operator report data is public. Used only to exercise the pipeline. |
| Phishing URL training data (Phase 2) | **Real, public** (e.g. OpenPhish / PhishTank feeds) | The model must not be trained on data I wrote myself. |
| Thai SMS text (Phase 2) | TBD — public corpus if one exists, otherwise a small hand-labeled sample, clearly marked | Document the final choice here. |

This project does not use any internal data from any company. Results on synthetic data say nothing about real-world performance.

## Architecture

```
generate_reports.py ──► data/raw/reports_synthetic.csv   (5,000 reports + 100 duplicated rows)
                              │
                       load_duckdb.py
                              ▼
        ┌──────────────── DuckDB (triage.duckdb) ──────────────────┐
        │                                                           │
        │  raw.reports        5,100 rows   all columns as text,     │
        │  (as-is)                         nothing removed          │
        │      │                                                    │
        │      │  sql/01_clean.sql                                  │
        │      │    • cast types (timestamp, integer)               │
        │      │    • dedupe on report_id (-100 rows)               │
        │      │    • drop blank/NULL message_text                  │
        │      │    • drop report_count outside 1..1000             │
        │      │      (-150 report_ids in total)                    │
        │      ▼                                                    │
        │  clean.reports      4,850 rows                            │
        │      │                                                    │
        │      │  sql/02_mart.sql                                   │
        │      │    • priority_score = report_count (placeholder)   │
        │      │    • review_rank = rank() by count desc, time      │
        │      ▼                                                    │
        │  mart.triage        4,850 rows ranked for review          │
        └───────────────────────────────────────────────────────────┘
                              │
                       quality_checks.py
                         • raw: report problems only (INFO)
                         • clean: 6 checks must be 0, else exit code 1
                         • tested in tests/test_pipeline.py
```

## Quick start (Windows PowerShell)

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python src/generate_reports.py --rows 5000 --seed 42
python src/load_duckdb.py
python src/run_sql.py
python src/quality_checks.py
pytest -q
```
